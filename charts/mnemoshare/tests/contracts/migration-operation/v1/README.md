# Migration operation contract v1

This generated bundle is the sole current migration-operation contract. It is generated from the compiled process composition and persisted-format closure and describes the `mnemoshare-migrate` executable, its pre-1.0 reset/plan/apply/verify/status command grammar, governed process/profile IDs, persistence universes, digest transport, and the required plan-all -> down -> apply-and-verify-all -> up lifecycle.

The migration operation exclusively owns application-level schema and format evolution. Deployment adapters own explicit process down/up orchestration and must leave the application down after a committed migration failure; automatic rollback to the old writer is not permitted. The one-time `pre-1-reset-format-ledger` command requires both `--exclusive` and `--confirm-before-first-1.0`. Apply runs with `--exclusive --bootstrap-policy provision-untracked` after all application writers are drained and provisions only generated untracked carriers. Apply creates Starting status and truthful plan-load/persistence-open checkpoints before opening persistence, so the startup probe owns process startup as soon as the CLI grammar is validated. `--status` atomically publishes truthful bounded progress snapshots, and `status` is the backend-neutral liveness probe; lease refreshes never count as progress. Status files are at most 4096 bytes, with failure text limited to 2048 bytes, and are caller-owned single-link regular files with mode 0600 in a caller-owned parent that is neither group nor world writable; symlinks in every path component are rejected, and writes use fsync-file -> atomic rename -> fsync-parent durability. Timestamps more than the declared 30s future-clock skew are invalid. On an inactivity or absolute deadline, either the internal watchdog or external `status` fallback produces the same canonical stalled terminal. `--termination-file <status-dir>/termination.json` atomically publishes one immutable terminal (an existing terminal can only be retried byte-identically). `--termination-message-file <termination-message-file>` names the runtime-owned container termination message file at `<status-dir>/../termination-message`, outside the caller-owned status directory, and Kubernetes `container.terminationMessagePath` must equal that argument exactly. Kubelet bind-mounts its own root-owned file at that path before the container starts; a path inside the status directory would force the runtime to create that directory root-owned and break its caller-owned trust. After the durable terminal is published, the same bytes are written into the existing message file in place (write at offset zero, truncate to length, fsync; no create, no rename, owner and parent unverified, symlinks and non-regular targets refused). The flag is required: omitting it refuses the command before any progress is written, and a failed message write fails the command naming the path. The supplemental SQLite process lock covers the apply command only, while the durable database lease remains authoritative; deployment orchestration owns plan/down/verify/up. `--expect-contract-fingerprint` makes the target binary attest its embedded operation grammar before persistence is opened. `--planning-mode` is part of that grammar. `--universe` selects one generated external persistence universe. `--plan` selects the immutable plan artifact, and `--expect-plan-digest` independently asserts it.

`contract.json` is the generated canonical artifact. Re-run `go run -tags migrations ./tools/migrationoperationcontract -root . -check` to verify generated state. The v1 directory remains mutable until a public release freezes it.

Status I/O deadlines bound the caller, but an in-flight OS fsync or read worker goroutine may remain orphaned until the kernel returns; its canceled generation is forbidden from publishing a stale snapshot. Operators must account for this bounded orphan-worker behavior.

The supplemental SQLite process fence is currently proven only on Linux with ext4, XFS, Btrfs, or tmpfs, and with caller-owned single-link database and sidecar files; other hosts and filesystems are refused fail-closed. The durable database lease remains authoritative.

Plan, result, termination, deadline/outcome semantics and the progress snapshot grammar are normative structured data in `contract.json` and `progress-schema.json`; `progress-conformance.json` supplies one conforming snapshot for every state. A deadline outcome is settled only after durable canonical terminal publication; uncertain durability or a conflicting owned terminal fails the command and may leave the termination artifact absent. Plan writers and readers enforce the same 16 MiB maximum, and plan publication verifies a caller-owned, single-link regular 0644 inode both before and after publication. Plan, result, and durable termination publication create temporary files in the destination parent, then use temp-file fsync, same-parent atomic rename, and parent-directory fsync; downstream mounts must make that parent writable and keep temporary and final paths on one filesystem. Result publication is limited to 4096 bytes and accepts a rename-error retry only after the visible regular file has the expected generation/inode and exact bytes, followed by parent fsync and generation revalidation. String bounds use the custom `x-mnemoshare-maxUtf8Bytes` keyword because JSON Schema `maxLength` counts Unicode code points, not encoded bytes. Consumers must apply the published UTF-8 byte-bound policy in addition to ordinary draft 2020-12 validation; generated tests exercise that policy at multibyte boundaries.
